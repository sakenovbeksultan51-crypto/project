# TableFlow — умный зал ресторана

Учебное веб-приложение для управления столиками и демонстрации трёх тем ИИ: нейронная сеть (неделя 9), Hidden Markov Models (неделя 7), интеллектуальный агент (неделя 1).

## Что работает

- Карта 12 столиков, вместимость, зоны зала, состояния «свободен / занят / нужна уборка / уборка».
- Посадка гостей, подтверждение первого подхода, таймеры и ручное подтверждение уборки.
- Лист ожидания с подбором минимального подходящего свободного стола.
- Интеллектуальный агент: уведомления при задержке первого подхода и уборки, без повторов в одном посещении.
- Загрузка своего видео или камера устройства. Разметка прямоугольных зон посадки. Реальное обнаружение людей с ONNX Runtime / YOLOv8n с детальным режимом увеличенных участков.
- HMM фильтрует последовательность наблюдений; вероятности и матрица переходов доступны в лаборатории ИИ.
- Раздельные демонстрационная и рабочая смены, серверное сохранение в Cloudflare D1, данные разделены по аккаунтам.
- Журнал, расчёт загрузки по времени, CSV, резервная копия и восстановление JSON.
- Адаптивная компоновка для компьютера и телефона.

## Запуск на компьютере

Нужен Node.js 24+ и npm. Сначала установите зависимости и соберите приложение:

```sh
npm ci
npm run build
npx wrangler d1 execute DB --local --config dist/server/wrangler.json --file drizzle/0000_superb_lady_ursula.sql
npm start
```

Откройте локальный адрес, напечатанный Wrangler (обычно http://localhost:8787). Для разработки после создания базы можно использовать `npm run dev`.

В локальном режиме localhost / 127.0.0.1 используется один локальный пользователь. В опубликованном приватном сайте идентичность устанавливает Sites. Проверка `Origin` и версия записи защищают от случайного перезаписывания из другой вкладки.

## Видеоаналитика

1. Сайт открывается в рабочей смене, в разделе «Видеоаналитика».
2. Загрузите реальное видео зала (например, MP4/H.264) или включите камеру.
3. После загрузки видео автоматически запускаются модель и поиск обеденных столов на первом кадре. Обнаруженные столы появляются на карте по положению в кадре. Авторазметку нужно проверить; при ошибке поставьте анализ на паузу и выделите области посадки вручную.
4. При отсутствии автозон выберите стол и нарисуйте прямоугольник. После разметки нажмите «Завершить разметку», затем «Распознавать людей».
5. Веса YOLO (около 13 МБ) и ONNX Runtime (около 11 МБ) входят в сайт и загружаются с того же адреса. Подключение к Google не требуется. При ошибке показывается сообщение; демо не подменяет результат нейросети.
6. После ухода гостей стол считается требующим уборки. Начало и окончание уборки подтверждает сотрудник.

Видеофайлы и кадры обрабатываются в браузере и не отправляются на сервер. В базе хранятся состояния, события и координаты зон. При открытии другого видео зоны сбрасываются, так как ракурс мог измениться. При переходе в другие разделы анализ продолжает работать, карта и аналитика обновляются из того же состояния. Закрытие страницы или смена режима останавливает обработку. Перемотка останавливает анализ — его нужно возобновить кнопкой.

## Учебные алгоритмы

- **Нейронная сеть:** YOLOv8n: проведены эксперименты COCO128 и COCO2017. Новый запуск: 768 обучающих изображений, включая 256 без людей, и 192 проверочных. Выбор весов и точные метрики — в `ml/precision-report.json`; старый эксперимент сохранён в `ml/report.json`. Она определяет людей, но не различает гостя и официанта. Один человек назначается не более чем одной зоне.
- **HMM:** состояния free / occupied / dirty; переходы и эмиссии заданы вручную. Используется прямой вероятностный фильтр. Изменение состояния требует вероятности > 0.86 и минимум трёх согласованных наблюдений. Это вероятность модели, не измеренная точность системы. Cleaning — подтверждённое сотрудником состояние, обработка камерой для него приостановлена.
- **Агент:** наблюдает состояние и время, проверяет правила, создаёт объяснимую задачу. Подтверждение первого подхода и уборки выполняется человеком.

## Границы версии

Это учебный MVP. Нужны реальные ресторанные записи и ручная разметка для измерения точности, ложных уведомлений и задержки. Анимационный ролик из задания — визуальный референс, не обучающая выборка. Объединение столов, бронирование, отдельные аккаунты персонала, внешние push-уведомления и прямое подключение RTSP не реализованы. Несколько устройств одного аккаунта могут загрузить смену; при параллельных изменениях второй редактор получит конфликт и должен загрузить серверную версию. Фоновая работа при закрытой странице не выполняется.

Подготовленный сценарий использует смоделированные наблюдения и подписан «Демонстрационная смена». Его можно показывать без камеры. Встроенная нейросеть проверена на реальной фотографии и пустом кадре. Точность в ресторане ещё не измерялась.

## Улучшенный детектор и эксперимент обучения

Текущая модель — YOLOv8n (Ultralytics, AGPL-3.0), ONNX Runtime — MIT. Модель и WebAssembly входят в сайт. В детальном режиме обрабатываются весь кадр и четыре перекрывающихся увеличенных участка, рамки объединяются NMS. По умолчанию используется полный кадр с порогом 45%; его можно изменить в видеоаналитике. Цена детального режима — более медленная обработка.

Скрипт `ml/train.py`, точные списки train/validation и метрики находятся в `ml/report.json`. COCO128 — маленький набор для проверки процесса обучения, а не подтверждение качества в ресторане. Предобученные веса могли видеть эти COCO-изображения. Данные конкретного ресторана и отдельный тестовый ролик нужны для независимой проверки сидящих, перекрытых и далёких людей.

Для дальнейшего обучения подходят COCO person (разнообразные позы), CrowdHuman/WiderPerson (перекрытия и мелкие люди) и вручную размеченные кадры ресторана. Наборы CrowdHuman/WiderPerson в текущем эксперименте не использовались. Новая модель не различает роли гостя и официанта.

### Удалённая камера
В «Видеоаналитике» первое устройство создаёт комнату кнопкой «Передавать камеру», второе вводит её 12-значный код кнопкой «Смотреть». На обоих устройствах нужен вход в один аккаунт. Один зритель, срок комнаты 2 часа, без аудио и записи. HTTPS API `/api/camera` хранит временные SDP в D1, защищает их идентификатором аккаунта и ключом устройства, использует optimistic concurrency. Видео передаётся напрямую через WebRTC; анализ выполняется на зрителе. Передающее устройство не запускает анализ автоматически. Оба устройства должны оставаться включёнными с открытой вкладкой. Доступ к пробуждению экрана запрашивается там, где поддерживается браузером. Используются публичные STUN-серверы Google. TURN не настроен, поэтому симметричный NAT и некоторые корпоративные/мобильные сети могут не соединяться; в таком случае нужна общая Wi-Fi сеть или последующая настройка TURN. Прогон на двух физических устройствах ещё необходим.

### Гостевой просмотр без аккаунта
Передающее устройство по-прежнему входит через ChatGPT. После включения камеры оно показывает локально созданный QR-код и ссылку `/watch#room=…&invite=…`. Ссылка содержит случайный секрет 256 бит, в D1 сохраняется только его SHA-256; фрагмент URL не отправляется с загрузкой страницы. Зритель нажимает «Открыть трансляцию» без регистрации. Владельцу доступен прежний вход по коду из своего аккаунта. Гость получает только SDP комнаты по отдельному ключу устройства, не может закрыть передачу или отправить предложение от лица камеры. Один зритель на комнату; остановка удаляет её, срок доступа — максимум 2 часа. Гостевая страница не обращается к базе смены напрямую. Наблюдения людей и разметка столов передаются через WebRTC владельцу; его устройство обновляет и сохраняет свою смену и возвращает карту гостю. Лист ожидания, имена гостей, настройки и журнал владельца в канал не передаются. После обновления страницы или смены устройства может понадобиться новая комната. Старые комнаты из версий до гостевого доступа нужно пересоздать. Ограничения WebRTC/STUN без TURN сохраняются.

### Уменьшение ложных обнаружений
По умолчанию выбран полный кадр с порогом person 45%. Дополнительные участки включаются отдельно для мелких дальних фигур. В этом режиме сначала находятся люди на полном кадре; слишком крупные и обрезанные внутренними границами участка рамки исключаются, вложенные рамки головы/торса объединяются с полной фигурой. Это эвристика: сильные перекрытия людей требуют отдельной оценки. Для нового обучения используется `ml/train_precision.py`, источники — `/models/yolo/datasets.json`, результаты — `/models/yolo/precision-report.json`. После обновления страницу просмотра нужно перезагрузить, чтобы получить новые настройки и код.


### Синхронизация карты и сброс смены
У камеры и зрителя теперь есть надёжный WebRTC DataChannel `tableflow-tables`. Владелец передаёт только таблицу состояний/зон, зритель — нормализованные рамки людей и калибровку. HMM и запись посещений выполняются на устройстве владельца; гость не управляет уборкой или сбросом. Авторазметка повторяется на следующих кадрах, пока нет зон. Если столешницы не видны, нужно выделить области посадки вручную; это возможно пальцем, в том числе на передающем устройстве. После разметки на зрителе нужно возобновить анализ. Кнопка «Сброс смены» доступна в шапке панели владельца, с подтверждением и возможностью скачать копию. Очередь, журнал, посещения, алерты и состояния очищаются, конфигурация/зоны сохраняются. Анализ приостанавливается, трансляция остаётся подключённой. Новый epoch защищает смену от старых сообщений/кадров. Подключённому зрителю отправляется новая карта; продолжение анализа запускается вручную. Ввод кода на главной странице открывает отдельный /watch, чтобы два авторизованных устройства не записывали одну смену параллельно. Для синхронизации обе страницы должны работать на новой версии. Проверки канала выполняются с имитацией RTCDataChannel; дополнительная проверка на двух реальных устройствах необходима.


### Дополнительный поиск столов
Авторазметка использует полный кадр и четыре увеличенных участка. Во время анализа поиск периодически повторяется; новые зоны добавляются после двух согласованных обнаружений, существующие зоны и номера сохраняются. Кнопка «Найти другие столы» запускает дополнительный поиск, а «Добавить стол вручную» позволяет разметить пропущенную область. Удалённая зона не добавляется повторно до смены источника. В удалённой трансляции разметка передаётся владельцу через DataChannel. Дополнительные проходы увеличивают время обработки.

Для столов проведён отдельный эксперимент обучения на COCO; он не подтвердил улучшение обнаружения мелких столов на отложенной выборке, поэтому в приложении оставлены исходные веса. Результаты: `ml/table-report.json` и `public/models/yolo/table-search-report.json`. Зоны и статусы нужно проверять на записи конкретной камеры.


### Защита от случайных проходов
Локальный анализ и владелец удалённой камеры сопоставляют обнаруженных людей с одной зоной и отслеживают их положение. Для нового подтверждения требуется не менее двух наблюдений и 1,5 секунды почти неподвижного присутствия; накопленное движение сбрасывает ожидание. Неопределённое присутствие не меняет состояние. После подтверждения занятость меняется на следующем обработанном кадре; момент зависит от скорости обработки. Обнаружение позы или личности не выполняется: стоящий рядом сотрудник, перекрытия и плохо размеченные зоны могут вызвать ошибку. Зоны необходимо корректировать так, чтобы проходы были вне области посадки; подтверждение занимает больше времени.

## Vercel deployment

The Vercel configuration builds the Vite app with Nitro and publishes `.vercel/output`. The app and its `/api/*` endpoints deploy as one full-stack service. The `ml/` directory contains model training and evaluation scripts, so it is not a separate HTTP service.

Connect a Neon database to the Vercel project and make sure it exposes `DATABASE_URL` (the app also accepts `POSTGRES_URL`). The app creates its `workspaces` table on the first API request. Without a database connection, the web page can load but saved workspaces and camera signaling will be unavailable.

For the hosted AI assistant, configure `OPENAI_API_KEY` and `OPENAI_MODEL` as server-side Vercel environment variables. Otherwise it falls back to local guidance.

## Защита и помощник

Тексты выступлений для четырёх участников, функции и ответы на вопросы: [docs/defense-4-members.md](docs/defense-4-members.md).

Прогноз ухода гостей реализован: среднее по завершённым визитам и условные вероятности ухода за 5, 10 и 15 минут. Уборка в прогноз времени ухода не входит.

Для облачного помощника доступен `ASSISTANT_PROVIDER=gateway` через Vercel AI Gateway. Используется OIDC-токен текущего серверного запроса. Модель по умолчанию — `nvidia/nemotron-3.5-lightning-free`; изменить её можно серверной переменной `AI_GATEWAY_MODEL`. AI Gateway может требовать карту и доступный лимит аккаунта даже для бесплатной модели. При отказе сервиса помощник возвращает явно обозначенную локальную сводку. Изображения, имена гостей и заметки очереди в контекст модели не передаются.
